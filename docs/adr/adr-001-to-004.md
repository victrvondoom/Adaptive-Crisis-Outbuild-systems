# ADR-001: Hybrid Optimization Strategy (MIP + VRP Decomposition)

## Status
ACCEPTED

## Date
2026-10-27

## Context
The AIDNEXUS resource allocation problem combines:
1. Multi-commodity assignment (which depot serves which request)
2. Vehicle routing (how to sequence deliveries)
3. Inventory constraints (don't over-allocate)
4. Time windows (delivery deadlines)
5. Multiple depots

Solving this monolithically as a single MIP would be computationally expensive for 200+ requests.

## Decision
Decompose the problem into two phases:
- **Phase 1 (MIP)**: Assignment — allocate requests to depots considering inventory, vehicle capacity, and priority
- **Phase 2 (VRP)**: Routing — for each depot's assignments, solve vehicle routing using OR-Tools routing library

## Consequences
- **Pro**: Better scalability; 200-request scenarios solvable in <15 seconds
- **Pro**: Easier to debug (assignment vs. routing issues are separable)
- **Pro**: Can use specialized OR-Tools solvers for each phase
- **Con**: Solution may not be globally optimal (decomposition gap)
- **Con**: Additional implementation complexity
- **Mitigation**: For hackathon, Phase 2 can be simplified to nearest-neighbor routing if time is short

# ADR-002: Three Agents with Clear Boundaries

## Status
ACCEPTED

## Date
2026-10-27

## Context
Agent design ranges from a single monolithic agent to many specialized micro-agents.

## Decision
Three agents, each with a well-defined trigger, tool set, and output contract:
1. Need-to-Mission (request interpretation)
2. Resource Strategist (planning and optimization)
3. Recovery & Accountability (disruption response)

## Consequences
- **Pro**: Clear responsibility boundaries
- **Pro**: Each agent can be tested independently
- **Pro**: Manageable complexity for a 7-day hackathon
- **Con**: Cross-agent communication adds latency
- **Mitigation**: Agent 3 can directly invoke Agent 2's planning tools for replanning

# ADR-003: Append-Only Audit Events

## Status
ACCEPTED

## Date
2026-10-27

## Context
Humanitarian operations require accountability. Decision history must be tamper-resistant.

## Decision
AuditEvent entity is append-only. No UPDATE or DELETE server actions. Every consequential action creates a new audit record with actor, timestamp, and state change.

## Consequences
- **Pro**: Complete, immutable decision history
- **Pro**: Supports compliance and accountability requirements
- **Con**: Storage growth over time (acceptable for hackathon scale)
- **Con**: Cannot correct erroneous audit entries (append corrections instead)

# ADR-004: Optimistic Concurrency for State Transitions

## Status
ACCEPTED

## Date
2026-10-27

## Context
Concurrent users (coordinator + system + agent) may attempt to transition the same entity simultaneously. This could cause double dispatches or conflicting state updates.

## Decision
Use a `Version` integer field on Mission, MissionAssignment, AidRequest, and InventoryItem. Every update includes a WHERE Version = expected_version check. On conflict, reject and force reload.

## Consequences
- **Pro**: Prevents double-dispatch and race conditions
- **Pro**: No pessimistic locking needed (better for ODC)
- **Con**: Requires retry logic on conflict
- **Con**: Additional complexity in server actions
